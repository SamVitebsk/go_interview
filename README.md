# go_interview

## Почему приведение `int64` в `int16` не проверяет диапазон?

В Go явное приведение типов **не выполняет проверок в runtime ради производительности** — операция компилируется в одну процессорную инструкцию.

Под капотом происходит **усечение битов (bit truncation)**: старшие 48 бит просто отбрасываются, а оставшиеся 16 бит интерпретируются как новое число. Никакой `panic` не возникает, данные искажаются «тихо»:
* `32768` превратится в `-32768` (старший бит станет знаковым минусом);
* `65536` превратится в `0` (все младшие 16 бит равны нулю).

### Как делать правильно:
1. При парсинге строк задавать `bitSize = 16` в `strconv.ParseInt(raw, 10, 16)` — функция сама проверит границы и вернёт `strconv.ErrRange`.
2. При работе с готовым `int64` — явно проверять диапазон `[-32768, 32767]` перед приведением.

## Zero value, `new(Bag)` и почему `make(Bag)` — ошибка

### 1. Различие типов `var b Bag` и `b := new(Bag)`
* **`var b Bag`** — объявляет переменную типа **`Bag`** (значение структуры). Память под поля структуры выделяется сразу, переменная содержит нулевое значение структуры.
* **`b := new(Bag)`** — объявляет переменную типа **`*Bag`** (указатель на структуру). Функция `new` выделяет память под структуру `Bag` и возвращает указатель на неё.
* Методы с pointer receiver `(b *Bag)` работают с обеими переменными одинаково: для `var b Bag` компилятор автоматически подставляет взятие адреса `(&b).Add(...)`.

### 2. Почему `new(Bag)` не создаёт `map` внутри структуры
* `new(T)` лишь выделяет память под тип `T` и заполняет её нулями (**zero value** для каждого поля структуры).
* Поле `items` имеет тип `map[string]struct{}`. Нулевое значение для типа `map` в Go — это **`nil`**.
* Функция `new` не вызывает никаких неявных конструкторов и не инициализирует вложенные хэш-таблицы. В результате поле `items` остаётся `nil map`.

### 3. Почему `make(Bag)` не является решением
* Встроенная функция `make(T, ...)` в Go жёстко зафиксирована в спецификации языка и предназначена **только для трёх типов**: `slice`, `map` и `chan`.
* Попытка написать `make(Bag)` приведёт к ошибке компиляции:
  `cannot make type Bag: must be slice, map, or chan`.
* Инициализировать внутреннюю `map` структуры можно либо явным конструктором (`NewBag()`), либо **ленивой инициализацией** в методах записи (`if b.items == nil { b.items = make(...) }`).

## Строки, байты и руны (string, byte, rune, UTF-8)

### Различие `len(s)` и `len([]rune(s))`

1. **`len(s)` возвращает количество байтов:**
   * Строка в Go под капотом представлена структурой `stringStruct { str unsafe.Pointer, len int }`.
   * Вызов `len(s)` выполняется за **$O(1)$**, так как он просто считывает готовое поле `len` из заголовка строки.
   * Для многобайтовых символов (например, кириллицы в UTF-8) результат `len(s)` не равен числу символов: для `s := "я"` `len(s) == 2`.

2. **`len([]rune(s))` возвращает количество Unicode-символов (рун):**
   * Преобразование `[]rune(s)` выполняет полное декодирование UTF-8 строки и аллоцирует в куче новый срез 4-байтовых элементов (`int32`).
   * Временная сложность — **$O(N)$**, пространственная сложность — **$O(N)$** (по 4 байта на каждый символ).
   * Для строки `s := "я"` `len([]rune(s)) == 1`.

3. **Идиоматичная альтернатива без аллокаций:**
   * Если нужно только узнать число символов без создания среза рун, используют `utf8.RuneCountInString(s)` из пакета `unicode/utf8`. Сложность: **$O(N)$ по времени, $O(1)$ по памяти**.

### Вопросы и ответы для собеседования

#### Что такое string в Go?
`string` в Go — это неизменяемая (immutable) последовательность произвольных байтов.
На уровне рантайма строка состоит из двух машинных слов (16 байт на 64-битной платформе):
* `str unsafe.Pointer` — указатель на неизменяемый базовый массив байтов в памяти;
* `len int` — длина последовательности в байтах.

Рантайм Go не валидирует UTF-8 при создании строки. Строка может содержать нулевые байты (`\x00`), бинарные данные или невалидные байты. UTF-8 — это конвенция стандартной библиотеки и строковых литералов, а не строгое ограничение типа `string`.

#### Почему строка immutable?
1. **Потокобезопасность (Concurrency Safety):** Неизменяемые строки можно параллельно читать из любого числа горутин без мьютексов, атомиков и риска Data Race.
2. **Бесплатный срез ($O(1)$ sub-slicing):** Операция `sub := s[2:5]` создаёт новый 16-байтный заголовок, указывающий на тот же базовый массив байтов без копирования памяти.
3. **Стабильность ключей в `map`:** Неизменяемость гарантирует, что хэш ключа-строки никогда не изменится и не нарушит инварианты бакетов хэш-таблицы.
4. **Оптимизации компилятора и линкера:** Строковые литералы безопасно размещаются в защищённой от записи секции данных бинарного файла (`.rodata`) и могут дедуплицироваться линкером.

#### Что возвращает индексирование строки?
Индексация `s[i]` возвращает **сырой байт (`byte`, он же `uint8`)** по индексу `i`, а не символ.
Это операция прямого чтения памяти по адресу `*(str + i)` со сложностью $O(1)$. Если символ закодирован несколькими байтами в UTF-8 (например, кириллица занимает 2 байта), `s[i]` вернёт только один байт кодовой последовательности, который сам по себе символом не является. Попытка изменить байт `s[i] = 'A'` вызывает ошибку компиляции.

#### Что возвращает range по строке?
Конструкция `for idx, r := range s` выполняет потоковое декодирование UTF-8 на лету и возвращает два значения:
1. `idx` (`int`): **байтовое смещение** (индекс байта в исходной строке, с которого начинается текущая руна). Для многобайтовых символов `idx` будет увеличиваться с шагом 2, 3 или 4 (`0, 2, 4...`).
2. `r` (`rune`, alias для `int32`): декодированную кодовую точку Unicode (Unicode Code Point).

#### Чем отличается byte от rune?
* **`byte`** — алиас (`type byte = uint8`). Занимает **1 байт** (8 бит, диапазон `0..255`). Используется для работы с сырыми бинарными потоками (`io.Reader`/`io.Writer`, сетевые пакеты), буферами байтов и ASCII-символами.
* **`rune`** — алиас (`type rune = int32`). Занимает **4 байта** (32 бита, со знаком). Используется для хранения кодовой точки Unicode (Code Point, диапазон от `0` до `0x10FFFF`). Четыре байта гарантируют вместимость любого допустимого символа стандарта Юникод (до 21 бита).

#### Почему len("я") == 2?
Встроенная функция `len()` для строк возвращает **размер в байтах**, а не количество символов.
Файлы с исходным кодом Go стандартизированы в кодировке UTF-8. В UTF-8:
* ASCII-символы занимают 1 байт;
* кириллические буквы (диапазон `U+0400`..`U+04FF`) кодируются **2 байтами**.
Буква «я» (`U+044F`) кодируется байтовой последовательностью `0xD1 0x8F`, поэтому длина среза байтов строки `"я"` равна 2.

#### Когда использовать []byte, а когда []rune?
* **`[]byte`** используют:
  * при работе с I/O, сериализацией (JSON, Protobuf), чтении из файлов и сети;
  * когда строка гарантированно ASCII и важна минимальная нагрузка на память (1 байт на элемент);
  * для создания мутабельных буферов (`bytes.Buffer`).
* **`[]rune`** используют:
  * для посимвольной обработки произвольного Unicode-текста (реверс строки, проверка палиндромов, разбиение на символы, регистронезависимое сравнение);
  * когда требуется произвольный доступ к $k$-му символу за $O(1)$ (`runes[k]`), что невозможно в сырой UTF-8 строке без линейного сканирования от начала.

#### Что произойдет при range по invalid UTF-8?
Рантайм Go не паникует и не прерывает цикл. При обнаружении некорректной последовательности байтов:
1. `r` принимает специальное значение **`utf8.RuneError`** (значение `\uFFFD`, символ замены ).
2. Смещение `idx` сдвигается **ровно на 1 байт**.
3. На следующей итерации декодер возобновляет попытку разобрать валидный UTF-8 со следующего байта (стратегия мягкого восстановления — *best-effort decoding*).

## Удаление элементов из среза (CopyWithout vs DeleteInPlace)

* **`CopyWithout`**: время $O(n)$, доп. память $O(n)$ — 1 аллокация в куче на $8n$ байт (`make([]int, 0, len(s))`), исходный массив не изменяется.
* **`DeleteInPlace`**: время $O(n)$, доп. память $O(1)$ — 0 байт, 0 аллокаций в куче, массив модифицируется на месте, освобождённый хвост зануляется (`clear`).

## Срезы в Go (Slice)

### Вопросы и ответы для собеседования

#### Из чего состоит slice?
Срез в Go — это 24-байтный дескриптор (структура `runtime.slice` на 64-битной архитектуре), состоящий из трёх полей:
* `array unsafe.Pointer` — прямой указатель на первый доступный элемент в базовом массиве (`underlying array`);
* `len int` — текущая длина среза (количество элементов, доступных для чтения/записи через индексацию `0 <= i < len`);
* `cap int` — ёмкость среза (максимальное количество элементов от `array` до физического конца базового массива).

#### Чем len отличается от cap?
* **`len` (length)** показывает, сколько элементов фактически находится в срезе в данный момент. Индексация `s[i]` разрешена строго в границах `0 <= i < len`. Попытка обратиться к элементу с индексом от `len` до `cap-1` вызывает панику `index out of range`, даже если память под них в базовом массиве уже выделена.
* **`cap` (capacity)** показывает максимальный размер, до которого срез может вырасти при помощи `append` без необходимости выделять новый базовый массив в куче.

#### Когда append выделяет новый массив?
* **Если `len + N <= cap`:** новый массив **не выделяется**. Значения дописываются напрямую в свободные слоты существующего базового массива по смещению `array + len`, а `append` возвращает новый дескриптор с увеличенным `len`. Если этот базовый массив разделяется с другими срезами, их данные за пределами их собственного `len` будут перезаписаны.
* **Если `len + N > cap`:** ёмкости недостаточно. Рантайм аллоцирует в куче **новый, более крупный массив**, копирует в него старые элементы (через `runtime.memmove`), дописывает новые и возвращает дескриптор, указывающий на новый адрес памяти. Исходный срез при этом продолжает указывать на старый массив.
* *Алгоритм роста (Go 1.18+):* до 256 элементов ёмкость удваивается ($2\times$). После 256 элементов рост плавно замедляется по формуле $\text{newcap} = \text{oldcap} + \frac{\text{oldcap} + 3 \times 256}{4}$ с последующим выравниванием под размерные классы аллокатора (`runtime.roundupsize`).

#### Чем nil slice отличается от empty slice?
Хотя для обоих срезов `len == 0` и `cap == 0`, между ними есть три принципиальных различия:
1. **Проверка на `nil`:**
   * У `nil slice` (`var a []int`): `a == nil` возвращает `true`. Указатель `array` равен `nil` (`0x0`).
   * У `empty slice` (`b := []int{}` или `c := make([]int, 0)`): `b == nil` возвращает `false`. Указатель `array` не равен `nil`, а указывает на специальный статичный объект рантайма `runtime.zerobase` (аллокация в куче не происходит).
2. **Сериализация в JSON (`encoding/json`):**
   * `nil slice` сериализуется в JSON как **`null`**;
   * `empty slice` сериализуется в JSON как пустой массив **`[]`**.
3. **Общее поведение:**
   Оба среза полностью безопасны для чтения в `for range`, вызовов `len()`, `cap()`, `copy()` и вызовов `append()`. Ни в один из них нельзя писать по индексу `s[0]` — обращение к любому срезу с `len == 0` гарантированно вызовет панику `index out of range`.

#### Почему subslice может удерживать большой массив в памяти?
Когда создаётся подсрез `small := big[:10]`, новый дескриптор `small` получает указатель `array`, ссылающийся на ту же область памяти базового массива, что и `big`.

Сборщик мусора (GC) в Go работает на уровне блоков памяти целиком: пока жив хотя бы один живой указатель на любую часть базового массива, **весь массив целиком считается достижимым и не может быть освобождён**. Если срез `big` занимал 1 ГБ, а долгоживущий `small` ссылается лишь на 10 элементов из него, весь 1 ГБ останется висеть в памяти.
*Решение:* скопировать нужные данные в независимый срез через `slices.Clone(big[:10])` или `append([]T(nil), big[:10]...)`.

#### Как передается slice в функцию?
Срез **всегда передаётся по значению (by value)**.
При вызове функции копируется только его 24-байтный заголовок (`array`, `len`, `cap`):
* **Изменение элементов `s[i] = v`:** будет видно вызывающему коду, потому что скопированный дескриптор содержит тот же адрес памяти `array`.
* **Изменение длины/ёмкости через `s = append(s, v)`:** **НЕ будет видно** вызывающему коду. Изменения происходят только в локальной копии заголовка функции. Если вызывающему коду нужен обновлённый срез, функция обязана возвращать его явно (`return s`) либо принимать указатель на срез `*[]T`.

#### Что такое full slice expression?
Full slice expression (3-индексный срез) — это синтаксис вида **`s[low:high:max]`**, который позволяет явно ограничить ёмкость (`cap`) результирующего среза:
$$\text{len} = \text{high} - \text{low}, \quad \text{cap} = \text{max} - \text{low}$$

*Зачем он нужен:*
Если сделать обычный срез `b := a[:2]` от массива `a := []int{1, 2, 3}`, у среза `b` будет `len = 2`, но `cap = 3`. Последующий `b = append(b, 100)` перезапишет третий элемент исходного массива `a[2] = 100`.
Синтаксис `b := a[:2:2]` принудительно задаёт `cap = 2`. Теперь при вызове `append(b, 100)` рантайм увидит, что ёмкости не хватает, и выделит **новый изолированный массив**, сохранив исходный массив `a` в полной безопасности.

## Хеш-таблицы в Go (Map)

### Вопросы и ответы для собеседования

#### Какие типы допустимы как ключи?
Ключом может быть любой тип, для которого компилятор может определить операторы сравнения на равенство (`==` и `!=`), то есть удовлетворяющий ограничению `comparable`:
* **Допустимы:** примитивные типы (`int`, `float`, `string`, `bool`), указатели (`*T`), каналы (`chan T`), массивы фиксированного размера `[N]T` (если элементы `T` сравнимы), структуры `struct` (если все их поля сравнимы), а также интерфейсы `any`/`interface{}`.
* **Недопустимы (ошибка компиляции):** срезы (`[]T`), мапы (`map[K]V`), функции (`func()`).
* **Senior-нюансы:**
  1. Интерфейс компилируется как допустимый ключ, однако если в runtime в интерфейс положить несравнимый тип (например, `slice`), обращение к мапе вызовет `panic: runtime error: hash of unhashable type`.
  2. Типы `float32`/`float64` формально разрешены, но использовать их крайне не рекомендуется из-за спецификации IEEE 754: значение `NaN != NaN`, поэтому записанное по ключу `math.NaN()` значение будет невозможно извлечь через `m[math.NaN()]`.

#### Чем чтение отсутствующего ключа отличается от comma ok?
При обычном чтении `val := m[key]` в случае отсутствия ключа Go всегда возвращает нулевое значение типа (`zero value`).
* **Проблема:** Невозможно отличить ситуацию, когда ключ реально существует в мапе со значением по умолчанию (`map[string]int{"status": 0}`), от ситуации, когда ключа в мапе нет вообще.
* **Решение (comma ok):** Синтаксис `val, ok := m[key]` возвращает булев флаг `ok`. Рантайм проверяет наличие ключа через внутреннюю функцию `runtime.mapaccess2`: `ok == true` выставляется только тогда, когда ключ физически присутствует в бакете таблицы.

#### Что разрешено делать с nil map?
Неинициализированная переменная `var m map[K]V` является `nil`-мапой (указатель на заголовок `*runtime.hmap == nil`).
* **Разрешено (безопасно, без паники):**
  * Читать: `val := m[key]` (возвращает `zero value`);
  * Проверять через comma ok: `val, ok := m[key]` (возвращает `val = zero, ok = false`);
  * Запрашивать длину: `len(m)` (возвращает `0`);
  * Удалять ключи: `delete(m, key)` (no-op, операция игнорируется);
  * Обходить в цикле: `for k, v := range m` (безопасно выполняет 0 итераций).
* **Запрещено:**
  * Запись `m[key] = val` немедленно вызывает **`panic: assignment to entry in nil map`**, так как базовой структуры `hmap` и массива бакетов в памяти физически не существует.

#### Гарантирован ли порядок range?
**Нет, порядок обхода мапы намеренно не гарантирован и рандомизируется при каждом запуске.**
* **Под капотом:** При каждом выполнении `for range` рантайм Go генерирует случайное число (`fastrand()`) и выбирает случайный начальный бакет и случайное смещение внутри бакета (`runtime.mapiterinit`).
* **Зачем это сделано:** Авторы языка сделали это намеренно, чтобы разработчики не полагались на порядок элементов хеш-таблицы: при добавлении новых ключей и эвакуации бакетов (*rehashing*) физический порядок элементов в памяти всё равно непрерывно меняется.
* **Как получить стабильный порядок:** Извлечь ключи в срез (`keys := make([]K, 0, len(m))`), отсортировать его (`slices.Sort(keys)`) и итерироваться по нему.

#### Почему поле структуры из map нельзя изменить напрямую?
Попытка `m["id"].Name = "Bob"` для `map[string]User` приводит к ошибке компиляции: `cannot assign to struct field in map`.
* **Причина (неадресуемость):** Элементы мапы не являются адресуемыми (`cannot take address of m["id"]`). Хеш-таблица в Go динамически масштабируется: при превышении коэффициента загрузки (*load factor > 6.5*) или переполнении бакетов происходит рост (*evacuation*), и бакеты перемещаются на новые адреса в куче. Если бы компилятор разрешал брать указатель на внутреннее поле структуры в мапе, при следующем росте мапы этот указатель стал бы висячим (*dangling pointer*).
* **Следствие:** Выражение `m["id"]` возвращает **временную копию** структуры по значению, а мутация временного значения бессмысленна и заблокирована компилятором.
* **Решение:**
  1. Скопировать структуру, изменить поле и перезаписать: `u := m["id"]; u.Name = "Bob"; m["id"] = u`.
  2. Либо изначально хранить в мапе указатели: `map[string]*User`.

#### Когда map требует синхронизации?
Встроенная структура `map` в Go **не является потокобезопасной (not thread-safe)**.
* **Когда требуется:** Синхронизация обязательна всегда, когда хотя бы одна горутина выполняет **запись** (вставка, изменение `m[k] = v`, удаление `delete(m, k)` или рост мапы), пока другие горутины параллельно читают или пишут в эту же мапу.
* **Что произойдет без неё:** Рантайм Go проверяет флаг записи (`h.flags & hashWriting`). При обнаружении одновременного доступа рантайм вызывает **`fatal error: concurrent map read and map write`** (или `concurrent map writes`). Это фатальная ошибка рантайма: её **нельзя перехватить через `recover()`**, процесс немедленно аварийно завершается (`SIGABRT`).
* **Способы синхронизации:**
  1. `sync.RWMutex` (самый частый паттерн: `RLock()` для чтения, `Lock()` для записи);
  2. Модель актора (чтение и запись делегируются одной горутине-владельцу через каналы);
  3. `sync.Map` — только для двух сценариев: append-only кэши (ключи пишутся один раз и многократно читаются) или когда горутины работают с непересекающимися множествами ключей.

## Интерфейсы в Go (Interface)

### Вопросы и ответы для собеседования

#### Как тип реализует интерфейс?
Тип реализует интерфейс **неявно (structural typing / duck typing)**: ключевых слов вроде `implements` в языке нет.
* **Правило:** Тип удовлетворяет интерфейсу тогда и только тогда, когда в его набор методов (*method set*) входят все методы, объявленные в интерфейсе, с в точности совпадающими сигнатурами (имена, типы аргументов и возвращаемых значений).
* **Compile-time проверка:** Чтобы зафиксировать гарантию реализации на этапе компиляции, используют идиому:
  `var _ TargetInterface = (*ConcreteType)(nil)`
  Это не тратит память в рантайме, но при несовпадении сигнатур компилятор сразу завершит сборку ошибкой.

#### Почему интерфейс объявляют рядом с потребителем?
В Go действует идиоматичный принцип: **«Accept interfaces, return structs»** и размещение интерфейса на стороне клиента (*consumer-driven interfaces*).
* **Слабая связанность (Decoupling):** Пакет-реализатор не должен ничего знать о потребителях. Это устраняет циклические зависимости и делает модули независимыми.
* **Принцип разделения интерфейса (ISP):** Потребитель декларирует минимально необходимый ему контракт (часто из 1–2 методов, как `io.Reader`), не привязываясь к «раздутым» интерфейсам на 15–20 методов.
* **Изоляция в тестах:** Код, зависящий от узкого локального интерфейса, элементарно покрывается юнит-тестами с помощью локальных моков или стабов без генерации тяжелых мок-библиотек.

#### Из каких частей состоит interface value?
Любое интерфейсное значение на 64-битной архитектуре занимает **ровно 16 байт (2 машинных слова)** и на уровне рантайма (`runtime/runtime2.go`) состоит из двух указателей:
1. **Для пустого интерфейса `any` (`eface`):**
   * `_type *_type` — указатель на метаданные о конкретном типе;
   * `data unsafe.Pointer` — указатель на копию самих данных в памяти.
2. **Для интерфейса с методами (`iface`):**
   * `tab *itab` — указатель на структуру метаданных интерфейса и типа, включающую таблицу виртуальных методов (`fun [1]uintptr` — *vtable*);
   * `data unsafe.Pointer` — указатель на конкретные данные.

#### Когда интерфейс равен nil?
Интерфейсная переменная равна `nil` **строго тогда, когда ОБА её внутренних указателя равны `nil`**:
* **Главная ловушка (Typed nil):** Если переменной типа интерфейс присвоить типизированный указатель со значением `nil` (`var p *MyType = nil; var i MyInterface = p`), интерфейс **НЕ БУДЕТ равен `nil`**, так как `tab != nil` (он хранит тип `*MyType`), хотя `data == nil`.
* **Правило для `error`:** Если функция возвращает интерфейс `error` и ошибки нет, необходимо возвращать нетипизированный литерал **`return nil`**, а не типизированную nil-переменную, иначе проверка `if err != nil` ложно сработает.

#### Как receiver влияет на method set?
Тип получателя метода (*receiver*) строго определяет, входит ли метод в набор методов значения или указателя:
* **Value receiver `(t T)`:** метод входит в method set **и для `T`, и для `*T`**.
* **Pointer receiver `(t *T)`:** метод входит в method set **только для `*T`**.
* **Следствие для интерфейсов:** Если хотя бы один метод интерфейса реализован с pointer receiver `(t *T)`, то значение `T` этот интерфейс **не реализует** (ошибка компиляции). Интерфейс будет реализован только указателем `*T`.
* *Причина:* Для неадресуемых значений или копий компилятор не может безопасно взять адрес `&T`, поэтому компилятор запрещает неявное приведение `T` к интерфейсу с pointer-методами.

#### Чем безопасная type assertion отличается от небезопасной?
Утверждение типа (*type assertion*) извлекает конкретное значение из интерфейса:
1. **Небезопасная форма (`val := i.(T)`):**
   Если динамический тип внутри `i` не совпадает с `T`, рантайм выбрасывает неустранимую панику:
   `panic: interface conversion: interface is ..., not T`.
2. **Безопасная форма comma ok (`val, ok := i.(T)`):**
   Если типы совпадают: `val` получает приведенное значение, `ok = true`.
   Если типы не совпадают: `val` получает нулевое значение типа `T` (*zero value*), `ok = false`, **паники не происходит**.
* При множественных проверках типов идиоматично использовать конструкцию **`type switch`** (`switch v := i.(type)`).

## Обработка ошибок в Go (Error)

### Вопросы и ответы для собеседования

#### Что такое error в Go?
`error` — это встроенный интерфейс всего с одним методом:
```go
type error interface {
    Error() string
}
```
* **Errors are values:** Ошибки передаются и возвращаются как обычные значения (обычно последним аргументом).
* **Явный control flow:** В Go намеренно нет исключений (`try/catch`). Поток управления не прерывается неявно: вызывающий код явно проверяет `if err != nil`, что делает точки отказа прозрачными и детерминированными.

#### Чем errors.New отличается от fmt.Errorf?
* **`errors.New`:** Создает статический `*errors.errorString` за $O(1)$ без аллокаций на парсинг шаблона. Каждый вызов выделяет уникальный адрес в памяти: даже ошибки с одинаковым текстом не равны (`errors.New("a") != errors.New("a")`), что делает их идеальными для Sentinel errors.
* **`fmt.Errorf`:** Форматирует динамическую строку через `fmt.Sprintf` (интерполяция переменных) и поддерживает спецификатор `%w` для построения цепочек ошибок.

#### Для чего нужен %w?
Спецификатор `%w` (*wrap verb*) оборачивает исходную ошибку, создавая тип с методом `Unwrap() error` (или `Unwrap() []error` в Go 1.20+):
* **Сохранение первопричины:** Позволяет `errors.Is` и `errors.As` обходить цепочку причин сквозь любые слои оберток до корня.
* **В отличие от `%v`:** `%v` оставляет только текст и безвозвратно теряет структуру ошибки.
* **Нюанс API:** Оборачивание через `%w` делает внутреннюю ошибку частью публичного контракта пакета (leaky abstraction). Если связывать клиента с внутренней реализацией нельзя — используют `%v`.

#### Чем errors.Is отличается от errors.As?
* **`errors.Is(err, target)` (Identity Matching):** Ищет совпадение по **значению** ошибки. Обходит цепочку через `Unwrap()`, сравнивая через `==` или вызывая `Is(error) bool`. Используется для Sentinel errors (`ErrNotFound`, `context.Canceled`).
* **`errors.As(err, targetPtr)` (Type Matching):** Ищет ошибку конкретного **типа** и извлекает её данные через утверждение типа (*type assertion*) или `As(any) bool`. Используется для извлечения полей из Typed errors.
* **Важно:** `targetPtr` обязан быть **указателем на целевую переменную** (например, `&valErr`, тип `**ValidationError`), иначе рантайм вызовет `panic`.

#### Что такое sentinel error?
Предопределенная константная переменная ошибки уровня пакета (`var ErrNotFound = errors.New("not found")`):
* Маркирует известное дискретное состояние; именуется с префикса `Err...`.
* Проверяется **строго через `errors.Is(err, ErrNotFound)`**, так как `==` ломается при наличии оберток `%w`.
* **Плюсы и минусы:** Максимально просто и эффективно, но создает жесткую связь (*tight coupling*) между пакетами и не несет контекста (например, какой именно ID не найден).

#### Когда использовать typed error?
Кастомная структура с методом `Error() string`, применяемая когда вызывающей стороне нужны **структурированные метаданные** для программной обработки:
* Поля валидации (`Field`, `Reason`, отклоненное значение);
* Транспортные метаданные (HTTP статус-код, сетевой таймаут, retry-интервал);
* Извлекается клиентами через `errors.As(err, &target)`.

#### Почему panic не заменяет error?
* **`error`** — для ожидаемых штатных отказов (сеть, диск, невалидный ввод, таймаут). Это нормальный сценарий работы приложения.
* **`panic`** — исключительно для неисправимых программных сбоев (nil pointer dereference, выход за границы среза) или нарушения инвариантов запуска (`regexp.MustCompile`).
* **Почему не заменяет:**
  1. `recover()` перехватывает панику только в **своей горутине** — паника в фоновой горутине роняет весь бинарник.
  2. Раскрутка стека при `panic` тяжела для CPU и GC.
  3. Неявные переходы ломают предсказуемость логики.

#### Что такое typed nil error?
Ловушка двухсловной структуры интерфейса `(dynamic_type, dynamic_value)`. Интерфейс равен `nil` **только если оба указателя равны `nil`**:
```go
func Validate() error {
    var err *CustomError = nil // type = *CustomError, value = nil
    return err                 // Интерфейс НЕ nil!
}
```
* **Последствие:** Проверка `if err != nil` вернет `true`, сервис сочтет операцию ошибочной и может запаниковать при обращении к nil-указателю.
* **Правило:** При успехе всегда возвращать нетипизированный литерал **`return nil`**.

## Стандартная библиотека: Encoding, Net, HTTP, IO, Context

### Вопросы и ответы для собеседования

#### Чем json.Encoder отличается от json.Marshal?
* **`json.Marshal`:** Сериализует объект целиком в буфер памяти и возвращает готовый `[]byte` в куче. Оптимален, когда размер данных мал и известен заранее.
* **`json.Encoder`:** Потоково (*streaming*) пишет данные напрямую в `io.Writer` (сетевой сокет `http.ResponseWriter`, файл), снижая нагрузку на память при больших объемах. Автоматически добавляет символ переноса строки `\n`.
* **Архитектурный нюанс:** При потоковой записи в `http.ResponseWriter` ошибка сериализации может возникнуть в середине стрима, когда статус-код (`200 OK`) уже зафиксирован и отправлен клиенту — изменить его на `500 Internal Server Error` будет невозможно.

#### Что делает omitempty?
Тег `json:",omitempty"` исключает поле из сериализации, если его значение равно предопределенному «нулю»:
* `false`, числовой `0`, `nil`-указатели и `nil`-интерфейсы;
* Пустые строки `""`, массивы, слайсы и мапы с длиной `len == 0`.
* **Ловушка:** Для структур (например, `time.Time`) `omitempty` не работает, пока поле не станет указателем (`*time.Time`), так как не-указательная структура не входит в список проверяемых типов.

#### Какие поля struct сериализует encoding/json?
* **Строго экспортируемые (публичные) поля**, начинающиеся с заглавной буквы.
* Неэкспортируемые (приватные) поля полностью игнорируются пакетом `encoding/json` из-за отсутствия доступа через рефлексию (`reflect`).
* Экспортируемое поле можно явно исключить с помощью тега `json:"-"`.

#### Что произойдет, если вызвать Write до WriteHeader?
* `http.ResponseWriter` неявно отправит заголовки с кодом по умолчанию — **`200 OK`**.
* Любой последующий вызов `w.WriteHeader(code)` (например, `w.WriteHeader(http.StatusNotFound)`) будет проигнорирован рантаймом с выводом предупреждения в лог: `http: superfluous response.WriteHeader call`.
* **Правило:** `w.Header().Set(...)` вызывается первым, затем `w.WriteHeader(code)`, и только в конце — `w.Write(body)`.

#### Почему http.Client без timeout опасен?
* В `http.DefaultClient` поле `Timeout` по умолчанию равно **`0` (таймаут отсутствует / бесконечен)**.
* **Последствия в продакшене:** Медленный, повисший или атакующий внешний сервис заблокирует вызывающую горутину навсегда. Это приводит к утечке горутин (*goroutine leak*), исчерпанию пула TCP-сокетов, файловых дескрипторов операционной системы и падению сервиса по OOM.
* **Правило:** Всегда настраивать `client.Timeout` и передавать `context.WithTimeout` в `http.NewRequestWithContext`.

#### Для чего нужен Request.Context()?
* **Распространение сигнала отмены (Cancellation):** Контекст запроса отменяется (`<-ctx.Done()`), если клиент закрыл вкладку, оборвал TCP-соединение или сработал таймаут чтения. Это позволяет немедленно прервать тяжелые SQL-запросы и походы во внешние API, освобождая ресурсы.
* **Дедлайны и таймауты:** Ограничение общего времени обработки запроса внутри цепочки middleware.
* **Request-scoped значения:** Безопасная передача сквозных метаданных запроса (Trace ID, Request ID, данные авторизованного пользователя).
* **Ловушка:** Нельзя передавать `r.Context()` в фоновые асинхронные горутины, переживающие хендлер (для фона используют `context.WithoutCancel`).

#### Почему io.Reader и io.Writer так часто используются?
* **Принцип разделения интерфейсов (ISP):** Это атомарные контракты всего из одного метода (`Read` и `Write`).
* **Универсальность и компонуемость:** Позволяют прозрачно объединять в единые пайплайны файлы, сетевые сокеты, gzip-компрессоры, шифрование, HTTP-тела и буферы в памяти (`io.Copy`, `io.MultiReader`, `io.TeeReader`).
* **Zero-copy оптимизации:** Методы вроде `io.Copy` умеют определять интерфейсы `io.WriterTo` / `io.ReaderFrom` и задействовать системные вызовы ядра (например, `splice(2)` в Linux) для передачи байтов между дескрипторами напрямую в ядре без копирования в user-space.

## Инициализация пакетов и функция init()

### Вопросы и ответы для собеседования

#### Почему зависимость может изменить порядок вычисления переменных?
Компилятор Go строит направленный ациклический граф зависимостей (DAG — Directed Acyclic Graph) инициализации переменных на уровне пакета:
* Если переменная `var a = b + 1` зависит от `b`, то значение `b` обязано быть вычислено первым, независимо от того, в каком порядке строки физически написаны в файле.
* Порядок объявлений учитывается только тогда, когда между переменными нет взаимных зависимостей.
* **Циклическая зависимость (`var a = b; var b = a`):** компилятор не может определить базовый шаг и завершает сборку ошибкой: `initialization cycle for a`.

#### Когда выполняется init() относительно переменных пакета и main?
Порядок старта приложения в Go строго детерминирован:
1. **Инициализация импортируемых пакетов:** пакеты инициализируются снизу вверх по дереву импортов (каждый пакет инициализируется ровно один раз за жизнь процесса).
2. **Глобальные переменные пакета (`var`):** вычисляются строго **до** любых вызовов `init()`.
3. **Функции `init()`:** выполняются последовательно в одной горутине после инициализации всех переменных пакета.
4. **Функция `main.main()`:** стартует строго **после** завершения работы всех `init()` во всех пакетах программы.

#### Почему подключение к БД через init() затрудняет обработку ошибок?
Инициализация внешних ресурсов (БД, сетевых соединений, очередей сообщений) в `init()` является грубым антипаттерном в Go:
1. **Невозможность вернуть ошибку:** `init()` не возвращает `error`. При сетевом сбое единственный выход — аварийная остановка (`panic` или `log.Fatal`), что лишает приложение возможности сделать retry или плавно завершить работу.
2. **Невозможность передать `context.Context`:** нельзя ограничить время подключения таймаутом или прервать по сигналу ОС.
3. **Проблемы с тестированием (Unit testing nightmare):** импорт пакета в `*_test.go` мгновенно запускает его `init()`. Тесты начинают требовать поднятую реальную БД и падают в изолированном CI/CD окружении; подменить подключение на mock становится невозможно.
4. **Скрытый глобальный стейт:** нарушается принцип явной передачи зависимостей (*Explicit Dependencies*).
* **Сеньорское правило:** Любые операции с I/O, конфигами и базами данных должны выполняться **явно в `main()`** через конструкторы вида `NewDB(cfg Config) (*DB, error)`.

#### Что делает пустой импорт (import _ "...")?
Пустой импорт подключает пакет исключительно ради его **побочного эффекта инициализации (side-effect import)**:
* Компилятор вычисляет переменные уровня пакета и запускает его функции `init()`, но не связывает с пакетом идентификатор в текущем файле (нет неиспользуемого импорта).
* **Основной сценарий (Self-registration pattern):** регистрация драйверов баз данных в реестре `database/sql` (например, `import _ "github.com/lib/pq"` регистрирует драйвер postgres) или регистрация графических форматов в пакете `image`.

## Рефлексия и небезопасный Go (Reflection и Unsafe)

### Вопросы и ответы для собеседования

#### Чем reflect.Type отличается от reflect.Value?
* **`reflect.Type`:** Метаданные типа (статическая информация): имя типа, пакет, список полей структуры, сигнатуры методов, теги `StructTag`. Создается через `reflect.TypeOf(x)`. Не содержит значений и не может их изменять.
* **`reflect.Value`:** Конкретные данные переменной в памяти во время выполнения: чтение значений, разыменование указателей, мутация, приведение обратно в интерфейс через `v.Interface()`. Создается через `reflect.ValueOf(x)`.

#### Чем Kind отличается от Type?
* **`Kind`:** Базовая категория типа в рантайме Go (фиксированный enum: `reflect.Int`, `reflect.String`, `reflect.Pointer`, `reflect.Slice`, `reflect.Struct` и т.д.).
* **`Type`:** Конкретный объявленный тип программиста или стандартной библиотеки.
* *Пример:* для `type UserID int`: `Value.Kind()` равен `reflect.Int`, а `Type.Name()` равен `"UserID"`.

#### Что такое settable value?
Это `reflect.Value`, значение которого разрешено изменить в рантайме через методы `.Set...()` (например, `.SetInt()`, `.SetString()`):
* **Условие 1 (Адресуемость):** Переменная должна быть передана по указателю и разыменована через `.Elem()` (`reflect.ValueOf(&x).Elem()`), иначе рефлексия оперирует изолированной копией (`CanSet() == false`).
* **Условие 2 (Экспортируемость):** Поле структуры должно быть публичным (с заглавной буквы). Неэкспортируемые поля могут быть адресуемыми (`CanAddr() == true`), но менять их запрещено (`CanSet() == false`).

#### Где reflection оправдана?
Исключительно в инфраструктурном коде, где типы данных физически неизвестны во время компиляции:
* Сериализаторы и десериализаторы форматов (JSON, XML, YAML, Protobuf);
* ORM и мапперы строк баз данных в структуры (`sqlx`, `gorm`);
* Универсальные валидаторы DTO по struct-тегам (`validator/v10`);
* Инъекция зависимостей (Dependency Injection контейнеры).
* *В прикладной бизнес-логике reflection — антипаттерн из-за снижения читаемости, оверхеда на аллокации и потери проверок компилятора.*

#### Почему reflection может паниковать?
Методы пакета `reflect` строго привязаны к конкретным `Kind`:
1. **Невалидное значение:** Вызов методов на `reflect.ValueOf(nil)` (где `IsValid() == false`).
2. **Неподдерживаемый Kind:** Вызов `v.IsNil()` для примитивов (чисел/структур), вызов `v.Elem()` не на указателе/интерфейсе или `v.Field(i)` не на структуре.
3. **Нарушение доступа к приватным полям:** Вызов `item.Interface()` на неэкспортируемом (приватном) поле структуры (перед вызовом обязательна проверка `item.CanInterface()`).
4. **Попытка мутации non-settable значения:** Вызов `.Set()` при `CanSet() == false`.

#### Для чего нужен unsafe.Pointer?
`unsafe.Pointer` — специальный тип указателя, отключающий строгую проверку типов компилятора:
* Позволяет преобразовывать указатель на любой тип в указатель на любой другой тип (аналог `void*` в C).
* **Связь с GC:** Сборщик мусора Go распознает `unsafe.Pointer` как валидный указатель и **не удаляет** объект, на который он ссылается.
* **В отличие от `uintptr`:** `uintptr` — это просто целое число (числовое значение адреса), которое GC не отслеживает. Адресная арифметика `unsafe.Pointer(uintptr(p) + offset)` должна выполняться строго в одно неделимое выражение.

#### Почему unsafe может ломать переносимость?
* **Выравнивание (Alignment) и Padding:** Размеры структур и смещения полей (`Offsetof`) зависят от разрядности архитектуры (32-bit vs 64-bit) и правил выравнивания конкретного компилятора.
* **Порядок байтов (Endianness):** Прямое чтение байтов из памяти через указатели дает разный результат на Little-Endian (x86, ARM) и Big-Endian архитектурах.
* **Внутреннее устройство рантайма:** Раскладка заголовков срезов (`runtime.slice`), строк (`stringStruct`) и интерфейсов может меняться между версиями Go.

#### Когда generics лучше reflection?
Всегда, когда семейство типов известно на этапе **компиляции**:
* **Типобезопасность:** Ошибки несовпадения типов ловятся компилятором, а не приводят к паникам в проде.
* **Производительность:** Generics мономорфизируются (gcsape) без аллокаций в куче, динамических вызовов и рефлексивных проверок.
* **Читаемость:** Сигнатуры функций явно декларируют ограничения типов (`comparable`, `any`, интерфейсные контракты), не скрывая типы за `any`.

## Задача: nil в interface (Typed nil)

### Вопросы и ответы для собеседования

#### Из каких двух частей состоит interface value?
Любое интерфейсное значение в Go на 64-битной архитектуре занимает 16 байт (2 машинных слова) и на уровне рантайма представляет собой пару указателей:
1. **Динамический тип (dynamic type):**
   * Для пустого интерфейса `any` (`runtime.eface`): указатель `_type *_type` на метаданные конкретного типа.
   * Для интерфейса с методами (`runtime.iface`): указатель `tab *itab`, хранящий информацию о типе и таблицу виртуальных методов (*vtable*).
2. **Динамическое значение (dynamic value):**
   * Указатель `data unsafe.Pointer` на сами данные в памяти (или на копию данных в куче).

#### Когда interface равен nil?
Интерфейсная переменная равна `nil` **строго тогда, когда ОБА её внутренних указателя равны `nil`**:
```go
// interface == nil <==> (dynamic_type == nil && dynamic_value == nil)
```
Если переменная содержит хотя бы тип (даже если данные под ним равны `nil`), интерфейс **не равен `nil`**.

#### Почему typed nil error не равен nil?
Когда функция с возвращаемым типом `error` возвращает типизированный `nil`-указатель:
```go
func Validate() error {
    var err *ValidationError = nil
    return err // В интерфейс error упаковывается (*ValidationError, nil)
}
```
В возвращаемый интерфейс `error` записывается:
* `tab/type = *ValidationError` (указатель на метаданные типа не равен `nil`!);
* `data = nil`.
Так как тип известен, рантайм оценивает выражение `Validate() == nil` как **`false`**. Проверка `if err != nil` ошибочно срабатывает в вызывающем коде, приводя к скрытым багам и паникам при разыменовании.

#### Почему any((*int)(nil)) != nil?
Выражение `any((*int)(nil))` упаковывает типизированный nil-указатель типа `*int` в пустой интерфейс `eface`:
* Динамический тип интерфейса получает адрес структуры метаданных типа `*int` (`_type != nil`);
* Динамическое значение равно `nil` (`data == nil`).
Так как динамический тип присутствует, интерфейсное значение `eface` отлично от нуля (`!= nil`).

#### Почему reflect.Value.IsNil нельзя вызывать для любого kind?
Метод `reflect.Value.IsNil()` в рантайме Go строго проверяет допустимость операции:
* В Go понятие `nil` применимо **только к ссылочным типам и указателям**: `Chan`, `Func`, `Interface`, `Map`, `Pointer` (Ptr), `Slice`, `UnsafePointer`.
* Если вызвать `rv.IsNil()` на типах, не способных принимать значение `nil` (`Int`, `Float`, `String`, `Struct`, `Array`), рантайм сгенерирует фатальную панику:
  `panic: reflect: call of reflect.Value.IsNil on ... Value`.
* **Правило:** перед вызовом `rv.IsNil()` обязательна фильтрация через `switch rv.Kind()`.

#### Как правильно возвращать отсутствие ошибки?
Если при выполнении функции ошибка не возникла, **всегда возвращайте нетипизированный литерал `return nil`**:
```go
// ПРАВИЛЬНО:
func Process() error {
    if err := do(); err != nil {
        return &MyError{Reason: "failed"}
    }
    return nil // возвращает нетипизированный nil (type == nil && value == nil)
}
```
Категорически запрещено объявлять переменную кастомной ошибки через указатель `var err *MyError` и возвращать её при успешном исходе.

## Method Set, Type Assertion и Type Switch

### Вопросы и ответы для собеседования

#### Что такое method set?
**Method set (набор методов)** — это специфицированное множество методов, ассоциированных с типом данных в Go. Именно method set определяет, удовлетворяет ли конкретный тип контракту того или иного интерфейса на этапе компиляции:
* Для значения конкретного типа `T` method set содержит **только методы с value receiver** (`func (t T)`).
* Для указателя `*T` method set содержит **все методы**: как с pointer receiver (`func (t *T)`), так и с value receiver (`func (t T)`).
* Для интерфейсного типа его method set совпадает со списком методов, объявленных в сигнатуре интерфейса.

#### Чем value receiver отличается от pointer receiver для interface?
* **Value receiver (`func (t T)`):** Метод оперирует изолированной копией значения. Метод входит в method set обоих типов — и `T`, и `*T`. Следовательно, переменной интерфейса можно присвоить как значение `T`, так и указатель `*T`.
* **Pointer receiver (`func (t *T)`):** Метод оперирует адресом исходного значения (может изменять поля и избегает накладных расходов на копирование). Метод входит в method set **только указателя `*T`**. Интерфейсу, требующему данный метод, можно присвоить **исключительно `*T`**. При попытке передать значение `T` компилятор выдаст ошибку.

#### Почему значение T может не реализовать интерфейс, который реализует *T (почему `var r Runner = Job{}` может не компилироваться)?
Если хотя бы один метод интерфейса `Runner` объявлен у структуры `Job` с pointer receiver (`func (j *Job) Run()`):
1. Метод `Run()` принадлежит method set типа `*Job`, но **отсутствует в method set типа `Job`**.
2. В отличие от прямого вызова метода на адресуемой переменной (`job.Run()`, где компилятор автоматически подставляет синтаксический сахар `(&job).Run()`), при присваивании интерфейсу `var r Runner = Job{}` компилятор строго проверяет **статический method set типа**, без авто-взятия адреса.
3. **Почему Go запрещает неявное взятие адреса при присваивании?** Значение внутри интерфейса копируется и становится **неадресуемым** (read-only копия в `data`). Если бы компилятор неявно создал указатель на эту временную копию, вызовы методов мутировали бы скрытую внутреннюю копию, а не исходную переменную, приводя к скрытым багам рассинхронизации состояния.

#### Что такое type assertion?
**Type assertion (утверждение типа)** — это runtime-операция проверки и распаковки динамического значения из переменной интерфейсного типа: `x.(T)`.
* Проверяет, совпадает ли динамический тип интерфейса `x` с конкретным типом `T` (или реализует ли динамический тип целевой интерфейс `T`).
* Позволяет получить доступ к методам и полям конкретного типа, скрытым за интерфейсом.

#### Почему `v.(T)` может panic?
Однозначная форма type assertion `val := v.(T)` вызывает фатальную панику `panic: interface conversion: ...` в двух ситуациях:
1. **Несовпадение динамического типа:** Реальный тип значения внутри интерфейса не равен `T` (и не реализует `T`).
2. **Интерфейс равен `nil`:** Если `v == nil`, у него нет динамического типа (`_type == nil`), поэтому любое приведение вызывает панику.
* **Безопасная альтернатива:** Всегда использовать форму с проверкой флага («comma-ok»): `val, ok := v.(T)`. Если приведение невозможно, `ok` равен `false`, `val` получает zero value типа `T`, а программа продолжает работу без паники.

#### Когда использовать type switch?
Конструкцию `switch x := v.(type)` следует использовать, когда:
* Интерфейсная переменная `v` может принимать **несколько различных конкретных типов** (или различных интерфейсов), и для каждого требуется своя специфическая ветка бизнес-логики.
* Необходима типобезопасная альтернатива длинной цепочке `if _, ok := v.(T1); ok { ... } else if _, ok := v.(T2) { ... }`.
* Реализуются инфраструктурные механизмы: сериализация/десериализация (AST, парсинг JSON/YAML), middleware, адаптеры, диспетчеризация разнородных событий (event handling) или детальная обработка ошибок (`switch err := err.(type)`).
* В каждой ветке `case ConcreteType:` переменная `x` автоматически приобретает статический тип `ConcreteType`.

## Generics и comparable

### Вопросы и ответы для собеседования

#### Что такое type parameter?
**Type parameter (параметр типа)** — это переменная типа, объявляемая в квадратных скобках при определении функции, типа или метода: `[T any]`.
* Служит плейсхолдером для конкретного типа данных, который подставляется при вызове или создании структуры (`type argument`).
* Обеспечивает строгую типобезопасность на этапе компиляции (Compile-Time Type Safety) без необходимости приведения типов и накладных расходов рефлексии.

#### Что такое constraint?
**Constraint (ограничение типа)** — это интерфейс, определяющий множество допустимых типов (Type Set), которые разрешено подставлять вместо параметра типа `T`.
* Задает разрешенный набор операций внутри generic-функции:
  * `any` (или `interface{}`) — разрешает любой тип, но запрещает любые специфические операции (кроме базовых присваиваний).
  * `comparable` — разрешает только типы, поддерживающие `==` и `!=`.
  * `cmp.Ordered` — разрешает только типы, поддерживающие операторы сравнения `<`, `<=`, `>`, `>=`.
  * Пользовательские интерфейсы с методами или наборами типов `~int | ~string`.

#### Чем any отличается от interface{}?
С технической точки зрения `any` — это **полный синтаксический псевдоним (type alias)** для `interface{}`:
```go
type any = interface{}
```
* Компилятор и рантайм трактуют их абсолютно идентично (одинаковая внутренняя структура `eface`).
* `any` был введен в Go 1.18 для лаконичности кода и визуального отделения параметров типов в generics от традиционных интерфейсов поведения.

#### Что значит ~int в constraint?
Оператор тильды `~T` означает **аппроксимацию типа (type approximation)** — множество всех типов, чей **базовый тип (underlying type)** равен `T`:
* Если ограничение задано как `int`, ему удовлетворяет только встроенный тип `int`.
* Если ограничение задано как `~int`, ему удовлетворяет как `int`, так и любые кастомные именованные типы, определенные на его основе:
  ```go
  type UserID int // Подходит под ~int, но НЕ подходит под просто int
  ```

#### Для чего нужен comparable?
`comparable` — это встроенный constraint, которому удовлетворяют типы, поддерживающие операторы сравнения `==` и `!=`.
* Он необходим для алгоритмов поиска элементов (например, `Contains`, `Unique`), структур множеств (`Set[T]`).
* Он является обязательным ограничением для ключей хэш-таблиц: `map[K comparable]V`.

#### Почему slice нельзя использовать как ключ map?
1. **Мутабельность:** Слайс ссылается на изменяемый массив в памяти. Изменение любого элемента слайса изменило бы его хэш-сумму, нарушив целостность бакетов хэш-таблицы и сделав значение неизвлекаемым.
2. **Сложность сравнения:** Для проверки равенства слайсов требуется глубокое поэлементное сравнение за линейное время O(N), тогда как операции поиска в `map` обязаны выполняться за константное время O(1).
3. **Семантическая неопределенность:** Неясно, что считать равенством двух срезов — совпадение адресов базовых массивов (`ptr`) или равенство их содержимого.
По спецификации Go типы `slice`, `map` и `func` являются несравнимыми (non-comparable).

#### Когда generics лучше interface?
* **Структуры данных и коллекции:** Обобщенные контейнеры (Set, Stack, Queue, Tree, LRU-кеш), типизированные конкретным элементом `T` без `any`.
* **Алгоритмы и утилиты для срезов/мап:** `slices.Sort`, `slices.Contains`, `maps.Keys`, `Filter`, `Map`.
* **Сохранение точного типа:** Когда возвращаемое значение функции должно иметь тот же тип, что и входной аргумент (`func Identity[T any](v T) T`), исключая небезопасный runtime type assertion.
* **Производительность:** Устранение боксинга значений в кучу (heap allocation) и динамической диспетчеризации вызовов методов.

#### Когда interface лучше generics?
* **Абстракция поведения:** Контракты бизнес-логики и подсистем ввода-вывода (`io.Reader`, `io.Writer`, `http.Handler`, `Storage`, `Sender`).
* **Внедрение зависимостей и слабая связанность:** Инверсия зависимостей (Dependency Injection) между пакетами и модулями.
* **Мокирование в тестах:** Подмена реальных внешних сервисов (БД, HTTP-клиентов) моками и стабами.
* **Гетерогенные коллекции:** Когда в одном срезе необходимо хранить элементы различных конкретных типов, объединенных общим поведением: `[]Worker`.

#### Разбор типов для Set[T comparable] и ограничения ~int

Даны типы:
```go
type UserID int
type Key struct { Region string; ID int }
type Report struct { Values []int }
```

**1. Какие из `UserID`, `Key`, `Report` и `[]int` подходят для `Set[T comparable]` и почему?**
* **`UserID` — подходит:** базовый тип — примитивный скаляр `int`, для которого определены операторы `==` и `!=`.
* **`Key` — подходит:** структура в Go является `comparable` тогда и только тогда, когда сравнимы **все её поля**. Поля `Region string` и `ID int` сравнимы, поэтому вся структура `Key` удовлетворяет `comparable`.
* **`Report` — НЕ подходит:** структура содержит поле `Values []int`. Срез в Go несравним, поэтому структура с полем-слайсом автоматически теряет свойство `comparable` (ошибка компиляции).
* **`[]int` — НЕ подходит:** срезы в Go не поддерживают операторы `==` и `!=` (за исключением сравнения с литералом `nil`).

**2. Почему `UserID` подходит для `~int`, но не подходит для ограничения только `int`?**
* `type UserID int` объявляет **новый именованный тип (defined type)**. В строгой системе типов Go `UserID` и `int` — это разные типы.
* Ограничение **`int`** (без тильды) требует **точного совпадения типа** — ему удовлетворяет строго встроенный тип `int`.
* Ограничение **`~int`** (с тильдой) проверяет **базовый тип (underlying type)**. Поскольку базовым типом для `UserID` является `int`, он удовлетворяет ограничению `~int`.

## Escape analysis, GC и память

### Вопросы и ответы для собеседования

#### Что такое escape analysis?
**Escape analysis (анализ побега)** — это статический анализ, выполняемый компилятором Go во время сборки (`go build -gcflags="-m"`), который определяет, где должно быть выделено место под переменную — на стеке горутины или в общей куче (heap).
* Если компилятор может доказать, что время жизни переменной строго ограничено текущим стековым кадром функции, память выделяется на **стеке** (быстрое выделение O(1) без участия GC).
* Если ссылка на переменную переживает возврат из функции, передается в `any`/`interface{}`, захватывается замыканием или размер объекта неизвестен/слишком велик — компилятор перемещает переменную в **кучу** (`escapes to heap`).
* Синтаксис `new`, `make` или взятие адреса `&` сам по себе **не определяет** место размещения.

#### Почему возврат &local в Go безопасен?
В отличие от языков вроде C/C++, где возврат адреса локальной переменной приводит к висячему указателю (dangling pointer) и неопределенному поведению (UB), в Go это **гарантированно безопасно**:
* Компилятор при помощи escape analysis видит, что адрес локальной переменной возвращается вызывающему коду.
* Компилятор автоматически выделяет память под эту переменную **в куче** (`moved to heap`).
* Переменная гарантированно живет в памяти до тех пор, пока на нее существует хотя бы одна достижимая ссылка в программе.

#### Чем stack отличается от heap?
* **Стек (Stack):**
  * Локален для каждой горутины (начинается с 2 КБ и динамически растет/сжимается).
  * Выделение и освобождение памяти тривиально (O(1)) — простым сдвигом регистра указателя стека `SP`.
  * **Не нагружает GC:** память мгновенно переиспользуется при завершении функции.
  * Обеспечивает максимальную локальность кэша процессора (L1/L2/L3 cache locality).
* **Куча (Heap):**
  * Общая область памяти для всех горутин программы.
  * Управляется аллокатором рантайма (по архитектуре TCMalloc: mcache, mcentral, mheap с разбиением на size classes).
  * Выделение памяти требует поиска свободных блоков и синхронизации.
  * Память освобождается **Garbage Collector (GC)**, что требует периодического сканирования ссылок и расхода CPU.

#### Что увеличивает давление на GC?
1. **Высокая частота аллокаций в куче (Allocation rate, allocs/op):** частые создания мелких объектов быстрее расходуют лимит памяти и заставляют триггер GC запускать сборку чаще.
2. **Множество указателей (Pointer-heavy структуры данных):** GC в Go использует параллельный трехцветный алгоритм пометок (tri-color mark-and-sweep). Фаза трассировки (mark) обязана обойти каждый живой указатель. Чем больше указателей в куче, тем дольше длится сканирование и тем больше CPU отбирается у полезной работы программы.
3. **Долгоживущие ссылки и крупные графы объектов:** заставляют GC удерживать память и повторно обходить объекты в каждом цикле сборки.
4. **Ненужный боксинг в `any` / `interface{}`:** упаковка примитивов и структур в интерфейс приводит к неявному уходу в кучу.

#### Почему subslice может удерживать память?
Срез в Go — это 24-байтный дескриптор `(array unsafe.Pointer, len int, cap int)`.
* При взятии подвыборки `small := large[:10]` указатель `small.array` продолжает ссылаться на **тот же самый базовый массив** в куче, что и `large`.
* Для сборщика мусора массив считается **единым неделимым объектом**. Пока жив хотя бы один маленький срез `small`, весь огромный базовый массив считается достижимым от корней и **не может быть освобожден GC**.
* **Решение:** явно скопировать нужные элементы в новый независимый срез:
  ```go
  small := make([]byte, 10)
  copy(small, large[:10])
  ```

#### Когда делать preallocation?
Предварительное выделение емкости (`make([]T, 0, capacity)` или `make(map[K]V, size)`) следует делать, когда:
* Ожидаемое количество элементов известно заранее (например, `len(source)`).
* Можно обоснованно оценить верхнюю границу размера коллекции.
* **Зачем:** исключает дорогостоящие промежуточные реаллокации в куче при росте слайса через `append`, избавляет от копирования памяти (`runtime.memmove`) и снижает фрагментацию кучи.
* **Ограничение:** не следует задавать чрезмерно завышенную емкость «на всякий случай», иначе неиспользуемая память будет впустую удерживаться в куче.

#### Почему оптимизировать нужно по профилю?
* **Интуиция обманчива:** из-за сложных оптимизаций компилятора (inlining, devirtualization, escape analysis) и работы CPU (кэши, спекулятивное выполнение) реальные узкие места почти никогда не совпадают с предположениями разработчика.
* **Профилировщик дает объективные метрики:** стандартный инструмент `pprof` (CPU profile, heap memory allocation `alloc_space`/`inuse_space`, block/mutex profile) и бенчмарки с флагом `-benchmem` показывают точные строки кода, создающие задержки и паразитные аллокации.
* Оптимизация без измерений приводит к усложнению архитектуры без реального прироста производительности («преждевременная оптимизация»).

## Ядра, процессоры, процессы и горутины (GMP, планировщик Go, Concurrency)

### Ключевые моменты
1. **Триада GMP:**
   * **G (Goroutine):** Легковесный поток в пространстве пользователя (user-space). Имеет начальный стек всего ~2 КБ, дескриптор `runtime.g` с указателем инструкций `PC`, указателем стека `SP` и состоянием (`_Grunnable`, `_Grunning`, `_Gwaiting` и др.).
   * **M (Machine):** Реальный поток операционной системы (OS thread). Выполняет машинные инструкции на процессорном ядре. Не знает о горутинах напрямую — выполняет код, предоставляемый логическим процессором `P`.
   * **P (Processor):** Логический процессор / контекст выполнения в рантайме Go. Количество `P` строго ограничено `GOMAXPROCS` (по умолчанию равно числу логических ядер ЦПУ). Владеет локальной очередью выполнения (Local Run Queue, LRQ на 256 горутин) и кэшем аллокатора памяти (`mcache`). Поток `M` обязан захватить `P`, чтобы исполнять Go-код.
2. **Модель M:N:**
   * M горутин мультиплексируются на N потоков операционной системы (через P контекстов). Это исключает накладные расходы ядра ОС на поддержание миллионов потоков.
3. **Стек горутины vs Поток ОС:**
   * **Поток ОС:** фиксированный стек (обычно 1–8 МБ), резервируется в виртуальной памяти ОС при старте, требует guard page.
   * **Горутина:** динамический непрерывный стек (contiguous stack), стартует с **2 КБ**. При нехватке памяти рантайм выделяет новый стек в 2 раза больше, копирует старый и переписывает внутренние указатели. При GC сжимается.
4. **Переключение контекста (Context Switch):**
   * **Поток ОС:** ~1–2 мкс (1000–2000 нс). Требует перехода User Space -> Kernel Space (Ring 3 -> Ring 0), сохранения всех регистров ЦПУ (включая FPU/AVX), смены таблиц страниц в MMU и частичного сброса кэша TLB.
   * **Горутина:** ~10–14 нс. Выполняется целиком в User Space без системных вызовов. Сохраняются только регистры общего назначения (всего ~14 штук: `PC`, `SP`, `DX` и др.).
5. **Планирование (Scheduler):**
   * Работает на основе **Work Stealing** (если локальная очередь `P` пуста, он крадет половину горутин у другого `P`, либо берет из глобальной очереди GRQ / network poller).
   * **Вытеснение (Preemption):** Начиная с Go 1.14 внедрено асинхронное вытеснение горутин на основе сигналов ОС (`SIGURG`), что предотвращает зависание планировщика в плотных циклах без вызовов функций.

### Ответы

#### 1. Чем горутина отличается от традиционного потока операционной системы?
* **Управление:** Поток ОС управляется ядром (kernel space), горутина управляется планировщиком Go runtime в пользовательском пространстве (user space).
* **Размер стека:** Поток ОС имеет фиксированный стек (обычно 1–8 МБ). Горутина стартует со стеком **2 КБ**, который динамически растет и сжимается.
* **Переключение контекста:** Поток ОС требует переключения контекста ядра, сброса процессорных кэшей и таблиц TLB (~1–2 мкс). Горутина переключается за десятки наносекунд внутри процесса без вызова ядра ОС.
* **Количество:** Потоков в системе можно создать тысячи, горутин — сотни тысяч и миллионы.

#### 2. Какую модель использует Go для управления горутинами и потоками? Объясните обозначения M и N.
Go использует **модель мультиплексирования M:N**:
* **M** (в формуле) — количество легковесных горутин приложения (может достигать сотен тысяч и миллионов).
* **N** (в формуле) — количество реальных потоков операционной системы (обычно равно `GOMAXPROCS` или числу логических ядер ЦПУ).
* **Суть:** Множество горутин (M) эффективно распределяются рантаймом Go для исполнения на небольшом пуле системных потоков (N).

#### 3. Как управляется время выполнения горутин в Go runtime?
Планировщик Go распределяет процессорное время с помощью гибридного механизма:
1. **Кооперативные точки передачи управления:** Вызовы системных функций, операции ввода/вывода (I/O, network poller), операции с каналами (`chan`), захват мьютексов (`sync.Mutex`), вызовы функций (проверка флага сплита стека `morestack`) и явный вызов `runtime.Gosched()`.
2. **Асинхронное вытеснение (Preemptive Scheduling, начиная с Go 1.14):** Фоновый системный поток мониторинга `sysmon` отслеживает горутины, работающие без смены контекста более 10 мс, и посылает потоку операционной системы сигнал `SIGURG`. Обработчик сигнала приостанавливает горутину и помещает ее обратно в очередь планировщика.

#### 4. Чем отличается планировщик Go от планировщика операционной системы?
* **Уровень работы:** Планировщик ОС работает на уровне ядра (kernel space) с аппаратными потоками и системными прерываниями. Планировщик Go работает в пользовательском пространстве (user space) внутри одного процесса ОС.
* **Область видимости:** Планировщик ОС ничего не знает о горутинах и видит только потоки `M`. Планировщик Go видит состояние всех горутин и распределяет их по потокам `M` через логические процессоры `P`.
* **Цели и накладные расходы:** Планировщик ОС должен быть универсальным для всех типов программ и процессов. Планировщик Go оптимизирован строго под модель исполнения Go (каналы, I/O, сетевой поллер) и не требует дорогостоящих системных вызовов для переключения контекста.

#### 5. Каковы основные различия в потреблении ресурсов между процессами, потоками и горутинами?
* **Процесс:** Самый тяжелый объект. Собственное изолированное виртуальное адресное пространство, таблицы страниц памяти, дескрипторы файлов, безопасность и квоты ОС. Потребление памяти — десятки мегабайт на старте.
* **Поток ОС:** Легче процесса. Разделяет адресное пространство и файлы с другими потоками процесса, но имеет собственный стек фиксированного размера (1–8 МБ) и структуры управления ядра ОС.
* **Горутина:** Самый легковесный объект. Живет внутри процесса, не имеет собственных сущностей в ядре ОС. Начальный стек всего 2 КБ, дескриптор в рантайме занимает всего несколько сотен байт.

#### 6. В чем заключается отличие в потреблении памяти между процессом, потоком и горутиной?
* **Процесс:** Мегабайты и гигабайты (отдельное виртуальное адресное пространство, таблицы страниц, стек, куча, сегменты кода и данных).
* **Поток:** Фиксированный стек (по умолчанию в Linux 2–8 МБ) плюс служебные структуры дескриптора потока в ядре. Память стека резервируется независимо от того, сколько реально используется.
* **Горутина:** Динамический стек, начинающийся всего с **2 КБ**. По мере глубоких вызовов стек удваивается (4 КБ, 8 КБ, 16 КБ...), а при сборке мусора (GC) неиспользуемая память стека освобождается и сжимается.

#### 7. Как происходит переключение контекста между процессами, потоками и горутинами? Сравните время переключения.
* **Между процессами (~1–2 мкс и более):** Переход в Ring 0, сохранение всех регистров, переключение указателя каталога таблиц страниц (`CR3` в x86), инвалидация TLB (кэша трансляции адресов), сброс кэшей процессора.
* **Между потоками одного процесса (~1–1.5 мкс):** Переход в Ring 0, сохранение регистров процессора, смена стека ядра/пользователя. Таблицы страниц не меняются, поэтому TLB не сбрасывается.
* **Между горутинами (~10–14 нс):** Переключение происходит в Ring 3 (без участия ядра). Сохраняются и восстанавливаются только ~14 регистров общего назначения (`PC`, `SP` и регистры данных), после чего поток `M` начинает исполнять инструкцию другой `G`.

#### 8. Почему создание горутин значительно дешевле, чем создание процессов и потоков?
* Не требуется обращаться к ядру ОС через системный вызов (`clone`/`fork`).
* Выделяется всего ~2 КБ памяти под стек из готового пула рантайма Go (вместо резервирования мегабайт и выделения виртуальных страниц ядром).
* Создание горутины `go f()` сводится к заполнению маленькой структуры `runtime.g` в куче и добавлению указателя в очередь `runq` логического процессора `P`.

#### 9. Какие ресурсы выделяются операционной системой для процессов, потоков и горутин?
* **Для процесса:** Ядро выделяет уникальный PID, виртуальное адресное пространство (VMA), таблицы страниц, дескрипторы открытых файлов, стек, структуры сигналов и учетные данные безопасности.
* **Для потока:** Ядро выделяет TID, регистровый контекст, стек потока фиксированного размера и очередь планирования ядра.
* **Для горутины:** Операционная система **напрямую ничего не выделяет**! Вся память выделяется процессом Go из уже выделенной ему кучи/стека, а планированием управляет Go runtime.

#### 10. Как работает планировщик Go при многозадачности с горутинами?
Планировщик Go использует схему **GMP** и алгоритм **Work Stealing**:
1. Каждый логический процессор `P` имеет локальную очередь задач (Local Run Queue, LRQ) на 256 горутин и одну приоритетную ячейку `runnext`.
2. Поток `M` берет горутину `G` из очереди своего `P` и выполняет ее.
3. Если локальная очередь пуста:
   * `P` пытается взять горутины из глобальной очереди (Global Run Queue, GRQ).
   * `P` проверяет завершившиеся сетевые операции в `Network Poller`.
   * `P` «крадет» половину горутин из локальной очереди другого случайного процессора `P` (*Work Stealing*).
4. Раз в 61 такт планировщик принудительно проверяет глобальную очередь GRQ, чтобы исключить голодание (starvation) горутин.

#### 11. Почему время переключения контекста между горутинами минимально?
1. **Отсутствие syscall:** Переключение не требует перехода в привилегированный режим ядра (Ring 3 -> Ring 0) и обратно.
2. **Минимум регистров:** Сохраняются только регистры общего назначения (около 14 штук), необходимые для возобновления функции. Регистры FPU/SSE/AVX не сохраняются, если они не задействованы на границе переключения.
3. **Общая память и кэш:** Все горутины работают в общем адресном пространстве процесса — таблицы страниц не переключаются, процессорный кэш L1/L2/L3 и TLB остаются горячими.

#### 12. В чем состоит основное преимущество использования горутин в Go по сравнению с потоками ОС?
* **Сверхвысокая масштабируемость (concurrency):** Возможность держать сотни тысяч и миллионы одновременных задач (например, активных сетевых соединений в веб-сервере) на скромном сервере без исчерпания RAM.
* **Дешевизна синхронизации:** Легковесные примитивы (каналы, select, sync) позволяют проектировать параллельные системы без дорогостоящей блокировки системных потоков ядра.

#### 13. Какие ограничения существуют при запуске процессов и потоков в операционной системе?
* **Лимиты ядра ОС:** Системные ограничения `ulimit -u` (максимум процессов/потоков на пользователя), `sys.kernel.pid_max`, `sys.vm.max_map_count`.
* **Потребление физической и виртуальной памяти:** Каждый поток требует 1–8 МБ стека. 10 000 потоков займут от 10 до 80 ГБ оперативной памяти только под стеки.
* **Деградация CPU при Context Switching:** При большом числе потоков процессор начинает тратить большую часть времени на переключение между ними (thrashing), а не на полезные вычисления.

#### 14. Каковы основные преимущества модели M:N, используемой в Go runtime для управления горутинами и потоками?
* Оптимальное использование ресурсов процессора: число реально выполняющихся потоков ОС равно количеству физических ядер (`GOMAXPROCS`), что исключает лишнее переключение контекста ядра.
* Блокировка одной горутины (например, на сетевом сокете) не блокирует поток ОС — рантайм просто переключает поток на другую готовую к выполнению горутину.
* Эластичность: если горутина выполняет блокирующий системный вызов (чтение диска), поток `M` отвязывается от `P`, а для `P` создается или берется из пула другой поток `M`, чтобы продолжить работу остальных горутин.

#### 15. Почему горутина может быть более эффективной, чем традиционный поток ОС с точки зрения ресурсов?
* Потребляет в ~1000 раз меньше памяти на старте (2 КБ против 2–8 МБ).
* Переключается в ~100 раз быстрее (10 нс против 1000–2000 нс).
* Не создает нагрузки на планировщик ядра операционной системы.
* Автоматически интегрирована с асинхронным Network Poller (epoll / kqueue / IOCP), преобразуя асинхронный I/O в синхронный и удобный для программиста код.

#### 16. Какой размер стека обычно имеет горутина в Go, и как он может изменяться?
* **Начальный размер:** **2 КБ** (2048 байт).
* **Рост стека (Contiguous Stack):** В прологе каждой функции компилятор вставляет проверку переполнения стека. Если памяти не хватает, вызывается рантайм-функция `morestack`, которая аллоцирует новый непрерывный блок памяти вдвое большего размера (4 КБ, 8 КБ...), копирует туда старый стек, обновляет все указатели и освобождает старый блок.
* **Максимальный размер:** По умолчанию 1 ГБ на 64-битных системах и 250 МБ на 32-битных (настраивается через `debug.SetMaxStack`).
* **Сжатие:** При сборке мусора (GC), если используется менее четверти выделенного стека, рантайм уменьшает размер стека вдвое.

#### 17. Как Go runtime минимизирует затраты при запуске большого количества горутин?
1. Пулы структур `runtime.g` (переиспользование освобожденных дескрипторов горутин без новых аллокаций).
2. Минимальный стартовый стек (2 КБ).
3. Локальные очереди выполнения у каждого `P`, не требующие глобальной блокировки при добавлении горутины.
4. Выделение памяти под стеки через собственный быстрый страничный аллокатор рантайма.

#### 18. Чем отличается использование памяти для горутин по сравнению с потоками и процессами?
* **Процесс:** Полная изоляция памяти. Обмен данными только через межпроцессное взаимодействие (IPC: сокеты, shared memory, pipes).
* **Поток:** Общая память процесса, но каждый поток имеет собственный громоздкий фиксированный стек, выделяемый ОС.
* **Горутина:** Общая память процесса, динамически растущий/сжимающийся стек минимального размера, находящийся под управлением сборщика мусора (GC) и рантайма Go.

#### 19. Какова роль компонента "P" в планировщике Go и как он влияет на выполнение горутин?
* **P (Processor)** — это абстракция логического процессора и контекста ресурсов, необходимых для исполнения Go-кода.
* **Количество:** Количество `P` строго фиксировано и задается переменной `GOMAXPROCS` (по умолчанию равно числу ядер ЦПУ).
* **Зачем нужен `P`:**
  1. Владеет **локальной очередью задач (LRQ)** на 256 горутин, благодаря чему горутины добавляются и извлекаются без глобального мьютекса.
  2. Содержит локальный кэш аллокатора памяти **`mcache`** — поток `M`, привязанный к `P`, аллоцирует объекты в куче быстро и без блокировок.
  3. Обеспечивает независимость горутин от системных потоков: если поток `M` заблокировался в системном вызове, `P` отсоединяется от него (*handoff*) и переходит к другому свободному `M`, продолжая исполнение остальных горутин.

#### 20. Почему Go runtime позволяет запускать сотни тысяч и более горутин одновременно, используя минимальные ресурсы?
Благодаря синергии четырех ключевых архитектурных решений:
1. **Крошечный начальный стек (2 КБ)** с динамическим непрерывным масштабированием (100 000 горутин займут всего ~200 МБ RAM).
2. **Модель M:N и планировщик GMP** с локальными очередями и алгоритмом **Work Stealing**, устраняющим конкуренцию за блокировки.
3. **Интегрированный Network Poller:** Ожидание сетевых пакетов переводится в `epoll`/`kqueue` без удержания и блокировки системных потоков ОС.
4. **Легковесное переключение контекста в user-space (~10–14 нс)** без задействования ядра ОС, смены таблиц страниц и сброса процессорных кэшей.

## Планировщик Go (Go Scheduler, Syscalls, Netpoller, Блокировки)

### ключевые моменты
1. **Поведение при системных вызовах (Syscalls):**
   * **Сетевой I/O (асинхронный):** Go переводит сетевые сокеты в неблокирующий режим (`non-blocking`). Когда горутина ждет чтения/записи в сеть, она паркуется (`gopark`), а дескриптор регистрируется в **Network Poller** (`epoll` в Linux, `kqueue` в macOS, `IOCP` в Windows). Системный поток `M` **не блокируется** и продолжает выполнять другие горутины из очереди `P`.
   * **Блокирующий Syscall (диск, вызовы Cgo, системные блокировки):** Поток `M` уходит в ядро ОС и физически засыпает. Чтобы другие горутины не простаивали, срабатывает механизм **handoff**: логический процессор `P` отсоединяется от заблокированного потока `M` и передается другому свободному потоку `M` (или создается новый `M`, если в пуле нет готовых). Когда блокирующий вызов завершается, горутина возвращается в очередь, а поток `M` пытается вернуть `P` или засыпает в пуле.
2. **Блокировки внутри Go (Каналы, Мьютексы, time.Sleep):**
   * **Каналы (`chan`):** При блокировке на пустом/заполненном канале горутина упаковывается в структуру `sudog`, ставится в очередь ожидания канала (`recvq`/`sendq`), переводится в статус `_Gwaiting` и паркуется вызовом `gopark`. Поток `M` освобождается для других задач. При появлении данных другая горутина будит ожидающую через `goready`, переводя ее в `_Grunnable`.
   * **`time.Sleep()`:** Горутина регистрирует таймер в системном таймере рантайма (четверичная куча таймеров привязана к `P`), переводится в режим ожидания `_Gwaiting` и освобождает поток `M`. Никакой системный поток ОС не блокируется!
3. **Роль `sysmon` (System Monitor):**
   * Фоновый поток рантайма Go, работающий **без логического процессора `P`** (не учитывается в `GOMAXPROCS`).
   * Задачи `sysmon`:
     1. Опрос сетевого поллера (`netpoller`) при простое.
     2. Вытеснение горутин, выполняющихся непрерывно более 10 мс (отправка сигнала `SIGURG`).
     3. Изъятие `P` у потоков `M`, зависших в системных вызовах (`retake`).
     4. Принудительный запуск Garbage Collection, если сборки мусора не было более 2 минут.
     5. Возврат неиспользуемых страниц памяти операционной системе (`scavenging`).

### Вопросы и ответы для собеседования по планировщику Go

#### 1. Как планировщик Go обрабатывает системные вызовы (syscalls)? В чем разница между сетевыми вызовами и файловыми операциями?
* **Сетевые системные вызовы (Network I/O):**
  * В Go сеть работает через неблокирующие дескрипторы и компонент **Network Poller**.
  * Когда горутина вызывает `net.Conn.Read()` и данных нет, рантайм Go не блокирует поток ОС, а переводит горутину в состояние ожидания `_Gwaiting` и регистрирует файловый дескриптор в `epoll`/`kqueue`. Поток `M` немедленно берет следующую горутину из очереди `P`. Когда данные приходят, `Network Poller` переводит горутину обратно в очередь готовности `_Grunnable`.
* **Файловые и блокирующие системные вызовы (File I/O, cgo):**
  * Файловый ввод-вывод в большинстве ОС (включая Linux) не поддерживает эффективный неблокирующий режим через epoll.
  * Поэтому при вызове `os.Open` или `file.Read` поток `M` входит в системный вызов ядра и блокируется. Рантайм Go отсоединяет логический процессор `P` от заблокированного потока `M` (**механизм Handoff**) и передает его новому или свободному потоку `M`, чтобы остальные горутины в очереди `P` продолжали исполняться.

#### 2. Что такое механизм Handoff P?
* **Handoff (передача процессора)** — это процедура отсоединения логического процессора `P` от системного потока `M`, когда `M` уходит в блокирующий системный вызов.
* Если `M` заблокирован в ядре более определенного времени (или компилятор знает, что syscall гарантированно блокирующий), рантайм или фоновый поток `sysmon` отбирает у `M` его контекст `P`.
* Контекст `P` со своей локальной очередью горутин привязывается к другому системному потоку `M` (берется из пула спящих потоков или создается новый). Таким образом, прогресс выполнения остальных горутин не страдает.

#### 3. Что происходит с горутиной и потоком при вызове `time.Sleep()`?
* Вызов `time.Sleep(d)` **не блокирует** системный поток операционной системы `M`.
* Горутина создает объект таймера в рантайме (таймеры распределены по структурам `P`), переводится в статус `_Gwaiting` и снимается с выполнения через внутреннюю функцию `gopark()`.
* Поток `M` сразу же переключается на выполнение других горутин из очереди `P`.
* Когда таймер срабатывает, планировщик переводит горутину в статус `_Grunnable` и возвращает ее в локальную очередь `P`.

#### 4. Что происходит на уровне рантайма при блокировке горутины на канале (`chan`)?
1. Если буфер канала пуст (при чтении) или полон (при записи), горутина не может продолжить работу.
2. Создается служебный дескриптор ожидания `runtime.sudog`, который связывает текущую горутину `G`, указатель на элемент данных и канал `hchan`.
3. Этот `sudog` помещается в соответствующую очередь канала: `recvq` (очередь ждущих читателей) или `sendq` (очередь ждущих писателей).
4. Вызывается функция `runtime.gopark()`, которая меняет статус горутины на `_Gwaiting` и освобождает поток `M`.
5. Поток `M` продолжает выполнять следующую готовую горутину.
6. Когда другая горутина выполнит операцию с каналом, она извлечет `sudog` из очереди, напрямую скопирует данные из стека в стек (оптимизация direct copy без промежуточного буфера) и вызовет `runtime.goready()`, возвращая ждущую горутину в очередь выполнения `_Grunnable`.

#### 5. Для чего нужна функция `runtime.Gosched()`?
* **`runtime.Gosched()`** — это добровольная уступка процессора текущей горутиной (*yield*).
* Горутина не блокируется, а переводится из состояния `_Grunning` в `_Grunnable` и кладется в конец глобальной очереди задач (`GRQ`).
* Текущий поток `M` переключается на исполнение следующей готовой горутины.
* Применяется в ситуациях кооперативного разделения ресурсов, в spin-lock ожиданиях или тяжелых вычислительных циклах для предотвращения голодания других горутин.

#### 6. Что такое Network Poller и как он устроен?
* **Network Poller** — это встроенный в Go runtime механизм асинхронного мультиплексирования ввода-вывода, реализованный поверх системных механизмов ОС (`epoll` в Linux, `kqueue` в macOS/BSD, `IOCP` в Windows).
* Он позволяет писать код сетевых серверов в синхронном, последовательном стиле (`conn.Read()`, `conn.Write()`), но при этом под капотом все операции выполняются асинхронно без блокировки потоков ОС.
* Планировщик опрашивает Network Poller в цикле планирования `findrunnable` и в фоновом потоке `sysmon`.

#### 7. Что такое `sysmon` и каковы его основные обязанности?
* **`sysmon` (System Monitor)** — это высокоприоритетный фоновый системный поток ядра Go runtime, который запускается вместе с программой.
* В отличие от обычных потоков `M`, `sysmon` работает **без захвата логического процессора `P`** и никогда не исполняет пользовательский Go-код.
* **Обязанности `sysmon`:**
  1. **Preemption (вытеснение):** Находит горутины, выполняющиеся дольше 10 мс, и инициирует их вытеснение (устанавливает флаг `preempt` и отправляет сигнал `SIGURG`).
  2. **Handoff P:** Отбирает процессор `P` у потоков `M`, застрявших в системных вызовах (`syscall`).
  3. **Опрос Network Poller:** Проверяет готовые сетевые сокеты, если планировщик давно их не опрашивал.
  4. **Force GC:** Запускает сборщик мусора, если GC не запускался более 2 минут.
  5. **Scavenging:** Возвращает физические страницы неиспользуемой памяти из кучи обратно операционной системе (через системный вызов `madvise`).

#### 8. Что происходит, если запустить бесконечный цикл `for {}` без вызовов функций?
* **До Go 1.14 (Кооперативное планирование):**
  * Планировщик проверял необходимость переключения контекста только в прологах функций (проверка сплита стека `morestack`).
  * Пустой цикл `for {}` без вызова функций никогда не доходил до пролога функции. Горутина намертво монополизировала поток `M` и процессор `P`. Если `GOMAXPROCS=1`, программа полностью зависала, и сборщик мусора (GC) не мог завершить фазу Stop-The-World (STW).
* **Начиная с Go 1.14 (Асинхронное вытеснение):**
  * Поток `sysmon` обнаруживает горутину, работающую >10 мс, и посылает потоку операционной системы сигнал `SIGURG`.
  * Обработчик сигнала операционной системы прерывает выполнение инструкций процессора, сохраняет регистры горутины и вставляет вызов переключения планировщика.
  * Горутина вытесняется даже из плотного цикла `for {}` без вызовов функций.

#### 9. Как устроена иерархия очередей в планировщике Go (LRQ vs GRQ)?
1. **Локальная очередь выполнения (Local Run Queue, LRQ):**
   * Закреплена за каждым `P`.
   * Вмещает максимум **256 горутин**.
   * Реализована как кольцевой буфер без блокировок (lock-free ring buffer), что обеспечивает максимальную производительность.
   * Имеет приоритетную ячейку **`runnext`** на 1 горутину: свежесозданная горутина запускается первой, сохраняя локальность процессорного кэша.
2. **Глобальная очередь выполнения (Global Run Queue, GRQ):**
   * Одна на весь рантайм Go.
   * Защищена глобальным мьютексом.
   * Сюда попадают горутины, если локальная очередь `P` переполнена (переносится половина LRQ), а также горутины после `runtime.Gosched()`.
3. **Алгоритм поиска работы (findrunnable):**
   * Проверить ячейку `runnext`.
   * Проверить локальную очередь LRQ.
   * Раз в 61 такт проверить глобальную очередь GRQ (защита от голодания).
   * Проверить Network Poller.
   * Выполнить Work Stealing (украсть 50% задач из LRQ другого `P`).

## Каналы в Go (Go Channels: hchan, nil-каналы, буферизация, select)

### Ключевые моменты

#### 1. Золотая матрица состояний каналов (Спрашивают на 99% собеседований!)
Поведение операций зависит от состояния канала (неинициализированный `nil`, открытый `open`, закрытый `closed`):

| Операция | Nil-канал (`var ch chan T`) | Открытый канал (`open`) | Закрытый канал (`closed`) |
| :--- | :--- | :--- | :--- |
| **Чтение (`<-ch`)** | **Блокировка навсегда** | Читает значение или блокируется | Возвращает zero-value и `ok == false` (после вычитывания остатков буфера) |
| **Запись (`ch <- v`)** | **Блокировка навсегда** | Записывает значение или блокируется | **Паника** (`panic: send on closed channel`) |
| **Закрытие (`close(ch)`)** | **Паника** (`panic: close of nil channel`) | Успешно закрывает | **Паника** (`panic: close of closed channel`) |

#### 2. Внутреннее устройство канала (`runtime.hchan`)
Канал в Go — это не примитив ядра ОС, а обычная структура данных в куче (`hchan`), на которую переменная канала ссылается как указатель:
* **`qcount`**: текущее количество элементов в буфере.
* **`dataqsiz`**: емкость буфера (`make(chan T, cap)`).
* **`buf`**: указатель на непрерывный кольцевой буфер в памяти (`circular ring buffer`).
* **`sendx`** и **`recvx`**: индексы кольцевого буфера для записи и чтения.
* **`recvq`** и **`sendq`**: двусвязные списки очереди ожидания (`waitq`), состоящие из структур `sudog` (заблокированные горутины, ожидающие чтения или записи).
* **`lock`**: внутренний легковесный спинлок (`runtime.mutex`), защищающий все операции с каналом.

#### 3. Небуферизованный vs Буферизованный канал
* **Небуферизованный (`make(chan T)` / `cap = 0`):**
  * Реализует синхронный механизм рандеву (*rendezvous*).
  * Отправка не завершится, пока получатель не будет готов принять данные.
  * **Оптимизация direct copy:** при передаче данных напрямую от отправителя к получателю данные копируются **из стека одной горутины прямо в стек другой** минуя буфер и память кучи!
* **Буферизованный (`make(chan T, n)`):**
  * Асинхронная отправка: отправитель не блокируется, пока кольцевой буфер `buf` не заполнится до отказа (`qcount == dataqsiz`).
  * Получатель не блокируется, пока в буфере есть хотя бы один элемент (`qcount > 0`).

#### 4. Паттерн динамического выключения веток в `select` через `nil`-канал
В конструкции `select` ветка с `nil`-каналом **блокируется навсегда и больше никогда не выбирается**. Это стандартный идиоматичный паттерн выключения завершившихся каналов:
```go
for ch1 != nil || ch2 != nil {
    select {
    case v, ok := <-ch1:
        if !ok {
            ch1 = nil // Ветка ch1 навсегда отключена из select!
            continue
        }
        fmt.Println("Из ch1:", v)
    case v, ok := <-ch2:
        if !ok {
            ch2 = nil // Ветка ch2 навсегда отключена из select!
            continue
        }
        fmt.Println("Из ch2:", v)
    }
}
```

### Ответы на вопросы

#### 1. Что такое nil-канал в Go?
* **nil-канал** — это переменная канального типа, которая не была инициализирована через `make()` либо которой явно присвоено значение `nil`.
* Под капотом переменная канала — это указатель на структуру `runtime.hchan`. У nil-канала этот указатель равен `0x0` (не указывает ни на какую структуру в куче).

#### 2. Как создается nil-канал в Go?
1. Неинициализированное объявление переменной (zero value для ссылочных типов):
   ```go
   var ch chan int // ch == nil
   ```
2. Явное присвоение значения `nil`:
   ```go
   ch := make(chan int)
   ch = nil // теперь ch стал nil-каналом
   ```

#### 3. Что произойдёт, если попытаться прочитать данные из nil-канала?
* Операция чтения `<-ch` **заблокирует текущую горутину навсегда**.
* Если в программе не останется других активных работающих горутин, рантайм Go аварийно завершит программу с фатальной ошибкой дедлока: `fatal error: all goroutines are asleep - deadlock!`.

#### 4. Что произойдёт, если попытаться записать данные в nil-канал?
* Операция записи `ch <- value` также **заблокирует текущую горутину навсегда**.
* При отсутствии других работающих горутин это приведет к панике дедлока всей программы.

#### 5. Чем отличается nil-канал от обычного канала?
* **Обычный канал (созданный через `make`):** имеет выделенную структуру `hchan` в куче, внутренний мьютекс, кольцевой буфер (для буферизованных) и очереди ожидания горутин `sendq`/`recvq`. Горутины разблокируются при появлении данных или при закрытии канала.
* **nil-канал:** не имеет структуры в памяти (`ptr == nil`). Любые операции чтения и записи паркуют горутину в состояние `_Gwaiting` навсегда, так как у nil-канала нет очередей ожидания, откуда планировщик мог бы ее когда-либо разбудить. Попытка закрыть (`close(ch)`) nil-канал вызывает немедленную панику (`panic: close of nil channel`).

#### 6. В каких случаях полезно использовать nil-канал?
Главный сценарий — **управление ветками в конструкции `select`**:
* В `select` кейс с nil-каналом становится неактивным (никогда не срабатывает).
* Это позволяет элегантно отключать каналы прямо на лету (например, после закрытия источника данных или по таймауту), не выходя из цикла обработки остальных каналов.

#### 7. Как можно избежать блокировки горутины при работе с nil-каналом?
1. **Использовать проверку перед операцией:**
   ```go
   if ch != nil {
       val := <-ch
   }
   ```
2. **Использовать неблокирующий `select` с веткой `default`:**
   ```go
   select {
   case val := <-ch:
       fmt.Println(val)
   default:
       // Выполнится немедленно без блокировки, даже если ch == nil!
       fmt.Println("Канал nil или не готов")
   }
   ```

#### 8. Как проверить, является ли канал nil в Go?
С помощью стандартного оператора сравнения:
```go
if ch == nil {
    // канал не инициализирован
}
if ch != nil {
    // канал готов к работе
}
```

#### 9. Что происходит, если горутина пытается записать данные в nil-канал без других горутин, которые могут их получить?
* Горутина переходит в состояние ожидания `_Gwaiting` навсегда.
* Так как других работающих горутин нет (некому разбудить рантайм), детектор дедлоков рантайма зафиксирует, что все потоки заснули, и выбросит фатальную ошибку `fatal error: all goroutines are asleep - deadlock!`.

#### 10. Может ли nil-канал быть полезен в реальных сценариях? Приведите примеры.
Да, наиболее частые реальные примеры:
1. **Мультиплексирование с завершением (Drain multiple channels):** Когда один из входящих каналов закрылся, мы зануляем его ссылку `ch = nil`, чтобы `select` перестал бесконечно вычитывать из него zero-value и переключился на оставшиеся каналы.
2. **Паттерн генератора с паузой (Rate Limiter / Pausable Worker):** Приостановка отправки данных путем временного подставления `out = nil` до снятия паузы.

#### 11. Как избежать ошибок при работе с nil-каналами в Go?
1. Всегда инициализировать каналы через `make(chan T, [cap])` перед отправкой или чтением.
2. Никогда не вызывать `close(ch)` на nil-канале (всегда проверять `if ch != nil`).
3. При проектировании API и структур передавать каналы явно через конструкторы с валидацией.

#### 12. Что происходит, если nil-канал передаётся в функцию, которая ожидает обычный канал?
* Функция успешно примет аргумент, так как `nil` является валидным значением типа `chan T`.
* Однако при первой же попытке функции прочитать из него или записать в него данные без использования `select default`, горутина зависнет в вечной блокировке. При попытке вызвать `close()` внутри функции произойдет паника.

#### 13. Как корректно управлять состоянием канала, чтобы избежать его состояния nil, если он должен быть использован?
1. Инициализировать канал в точке объявления:
   ```go
   ch := make(chan int)
   ```
2. В структурах инициализировать каналы через функции-конструкторы:
   ```go
   func NewWorker() *Worker {
       return &Worker{
           jobs: make(chan Job, 100),
           quit: make(chan struct{}),
       }
   }
   ```

#### 14. Как можно использовать nil-канал для временного отключения обработки в горутинах?
Используя замену переменной канала в цикле событий:
```go
var activeCh chan Task = tasksCh // Канал активен

for {
    select {
    case task := <-activeCh:
        process(task)
    case <-pauseSignal:
        activeCh = nil // ПАУЗА: select больше не будет опрашивать задачи
    case <-resumeSignal:
        activeCh = tasksCh // ВОЗОБНОВЛЕНИЕ: восстанавливаем ссылку на канал
    }
}
```

#### 15. Какие проблемы могут возникнуть при попытке использовать nil-канал для синхронизации данных между горутинами?
1. **Утечка горутин (Goroutine Leak):** Горутина, заблокированная на nil-канале, никогда не завершится, её стек и контекст навсегда останутся в памяти, усложняя работу Garbage Collector.
2. **Паника при закрытии:** Вызов `close()` на nil-канале приведет к краху программы.
3. **Общий дедлок программы (Deadlock):** Если главная горутина прямо или косвенно ожидает горутину, застрявшую на nil-канале.

## Оператор select в Go (Мультиплексирование, runtime.selectgo, таймауты)

#### 1. Главные правила работы `select`:
1. **Случайный выбор (Randomized Choice):** Если готовы сразу несколько веток `case`, `select` выбирает одну из них **псевдослучайно (равномерно)**. В отличие от `switch`, здесь нет порядка сверху вниз. Это предотвращает голодание (starvation) нижних кейсов.
2. **Неблокирующий опрос через `default`:** Если ни один канал не готов, а ветка `default` присутствует — управление немедленно переходит в `default` без блокировки горутины.
3. **Блокировка без `default`:** Если ни один канал не готов и `default` отсутствует, горутина переводится в статус `_Gwaiting` и засыпает, пока хотя бы один канал не станет готов.
4. **Пустой `select {}`:** Горутина блокируется **навсегда** (deadlock в `main`).
5. **Ветка с `nil`-каналом:** Блокируется навсегда и **игнорируется** планировщиком при выборе готового кейса.

#### 2. Внутреннее устройство алгоритма `runtime.selectgo`:
* **Фаза 1 (Lock Order):** Рантайм сортирует все каналы из всех кейсов по их адресам памяти `hchan`, чтобы при захвате внутренних блокировок исключить возникновение перекрестного дедлока (ABBA deadlock).
* **Фаза 2 (Poll Order):** Генерируется псевдослучайная перестановка индексов кейсов для обеспечения справедливого выбора.
* **Фаза 3 (Быстрый проход):** Проверяются все каналы в порядке `poll order`. Если хотя бы один готов к немедленному чтению/записи (или есть `default`), локи снимаются, операция выполняется, и `select` завершается.
* **Фаза 4 (Медленный проход / Ожидание):** Если ни один канал не готов, горутина создает по одному дескриптору `runtime.sudog` для каждого канала, помещает их во все очереди ожидания (`sendq`/`recvq`) этих каналов и засыпает вызовом `gopark()`. Как только один из каналов сработает, горутина просыпается, удаляет свои `sudog` из остальных каналов и выполняет код выигравшего кейса.

#### 3. Коварная ловушка: Закрытый канал в `select` и 100% загрузка CPU:
* Чтение из закрытого пустого канала возвращает zero-value и **не блокируется**.
* Если горутина крутится в цикле `for { select { case v := <-ch: ... } }` и канал `ch` закрывается, `select` будет **бесконечно и мгновенно выбирать этот кейс**, сжигая 100% ядер процессора!
* **Решение:** Проверять флаг `ok` и занулять канал:
  ```go
  case v, ok := <-ch:
      if !ok {
          ch = nil // Ветка отключена!
          continue
      }
  ```

#### 4. Коварная ловушка: `time.After()` внутри цикла:
* `time.After(d)` создает **новый таймер и новый канал на каждой итерации цикла**.
* Если в `select` часто приходят сообщения из рабочих каналов, ветка `time.After` никогда не сработает, но созданные таймеры останутся жить в памяти рантайма до истечения их срока. В высоконагруженном цикле это приводит к утечке памяти (**Memory Leak**).
* **Решение:** Создавать один `time.NewTimer` до цикла и делать `timer.Reset()` на итерациях.

### Ответы на вопросы

#### 1. Что такое оператор select в Go и как он работает?
* `select` — это управляющая конструкция языка Go, предназначенная для мультиплексирования операций ввода-вывода по нескольким каналам.
* Он отслеживает готовность нескольких каналов к операциям чтения или записи. Если готов один канал — выполняется его ветка. Если ни один канал не готов — горутина блокируется (если нет `default`).

#### 2. В чем основное отличие между оператором select и switch в Go?
* `switch` сравнивает **значения выражений** последовательно сверху вниз по порядку написания кейсов.
* `select` оценивает **готовность каналов к операциям ввода/вывода**. Если готовы несколько каналов, `select` выбирает один из них **случайно**, а не по порядку следования в коде.

#### 3. Как работает оператор select, если несколько каналов готовы для операции?
* Планировщик Go выбирает один готовый кейс **псевдослучайным образом с равномерным распределением**. Это исключает сценарий, когда верхние кейсы постоянно забирают весь трафик, а нижние голодают.

#### 4. Что произойдёт, если все каналы в select заблокированы?
* **Если есть ветка `default`:** `select` не блокируется, управление сразу передается в `default`.
* **Если ветки `default` нет:** текущая горутина блокируется (`_Gwaiting`) до тех пор, пока хотя бы один канал не станет готов. Если все горутины в программе заснули, рантайм вызовет панику дедлока.

#### 5. Как обработать несколько каналов с использованием select в Go?
Обычно `select` оборачивают в бесконечный цикл `for`:
```go
for {
    select {
    case msg := <-ch1:
        // обработка ch1
    case msg := <-ch2:
        // обработка ch2
    case <-ctx.Done():
        return // корректный выход
    }
}
```

#### 6. Что происходит, если в select несколько case могут быть выполнены одновременно?
* Рантайм выполняет псевдослучайную перестановку индексов (`poll order`) и выбирает первый выпавший готовый кейс. Остальные кейсы в этот запуск `select` игнорируются.

#### 7. Что вернёт оператор select, если один из каналов закрыт и пуст?
* Операция чтения `case v, ok := <-ch:` немедленно завершится успехом: `v` будет равно `zero value` типа канала, а флаг `ok` будет равен `false`.

#### 8. Как select работает с закрытым каналом, если в нем есть данные?
* Если в закрытом буферизованном канале остались непрочитанные данные, `select` успешно вычитывает их в штатном режиме: возвращается реальное значение и `ok == true`. Только после полного опустошения буфера канал начнет возвращать `zero value` и `ok == false`.

#### 9. Что произойдёт, если канал, в который записывают данные, будет закрыт?
* Попытка записи в закрытый канал внутри кейса `case ch <- val:` вызовет фатальную панику времени выполнения: `panic: send on closed channel`.

#### 10. Как в select определить, что канал был закрыт?
С помощью проверки второго булева возвращаемого значения (идиома *comma-ok*):
```go
case val, ok := <-ch:
    if !ok {
        // Канал закрыт и буфер пуст
    }
```

#### 11. Что произойдёт при чтении из закрытого канала, если в нем нет данных?
* Чтение завершится мгновенно без блокировки. Переменная получит значение по умолчанию (0, "", nil и т.д.), а `ok` станет `false`.

#### 12. Как избежать блокировки горутины при работе с закрытым каналом в select?
* Чтение из закрытого канала **никогда не блокирует** горутину (оно возвращает zero value).
* Опасность состоит в обратном — в **бесконечном неблокирующем цикле**. Чтобы избежать бесконечного холостого чтения, закрытый канал после обнаружения `!ok` зануляют: `ch = nil`.

#### 13. Как правильно использовать select для организации работы с несколькими каналами и таймаутами?
Для одноразового ожидания используют `time.After`:
```go
select {
case res := <-ch:
    fmt.Println("Результат:", res)
case <-time.After(2 * time.Second):
    fmt.Println("Таймаут операции")
}
```
Если `select` находится внутри цикла `for`, нужно использовать `time.NewTimer(d)` снаружи цикла и вызывать `timer.Reset(d)` на каждой итерации.

#### 14. В чем отличие между чтением из закрытого канала и чтением из пустого канала?
* **Из пустого открытого канала:** операция блокирует горутину до появления данных или закрытия.
* **Из закрытого пустого канала:** операция завершается немедленно без блокировки, возвращая zero value и `ok == false`.

#### 15. Как использовать канал с тайм-аутом в select?
Через связку с контекстом (`context.WithTimeout`) или `time.After`:
```go
ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
defer cancel()

select {
case data := <-ch:
    handle(data)
case <-ctx.Done():
    fmt.Println("Отмена по таймауту:", ctx.Err())
}
```

#### 16. Как обрабатывать случай, когда канал закрыт в select? Почему это важно?
* **Как обрабатывать:** При `!ok` необходимо предпринять действие: занулить канал `ch = nil` (чтобы выключить кейс из `select`) либо завершить работу горутины (`return` / `break`).
* **Почему это важно:** Если не обработать закрытие канала в цикле с `select`, программа уйдет в 100% утилизацию CPU, бесконечно считывая нулевые значения.

#### 17. Как корректно завершить работу с каналом, чтобы избежать блокировки горутин в select?
1. Следовать правилу владения каналами: **закрывать канал должен только писатель** (sender) и только один раз.
2. Для остановки группы читателей закрывать общий канал отмены `quit := make(chan struct{})`: закрытие канала мгновенно рассылает сигнал всем читающим горутинам (*broadcast*).
3. Использовать `context.Context` с отменой через `cancel()`.
